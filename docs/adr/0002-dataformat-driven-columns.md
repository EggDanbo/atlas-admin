# ADR-0002：表格列由服务端下发，schema 从视图代码提取

- 状态：已采纳
- 日期：2025-11

## 背景

110 个列表页，每个页面 8–14 列。列定义放在哪，决定了后续维护成本：

| 方案 | 问题 |
| --- | --- |
| 每个页面写死 `columns` 数组 | 100+ 处重复；列宽/对齐/合计各行其是；改风格要改 110 个文件 |
| 抽一个通用列配置常量 | 字段差异太大，配置会膨胀成第二个业务层 |
| 列由服务端下发（原系统做法） | 前端不知道有哪些字段，mock 无从生成 |

原系统是第三种：列由 `dataformat` 接口下发，前端按 `column + title + width + type` 渲染。
这个契约本身是好的——列顺序、列宽、显隐、筛选都能在后台配置，不用发版。
问题只在于：没有后端，这些配置从哪来。

## 决策

**保留契约，把配置的来源换成代码提取。**

```bash
pnpm mock:schema   # scripts/mock/extract-schema.mjs
```

脚本扫描 `src/views`，提取每个页面用到的字段与中文标题，产出：

- `MODULE_SCHEMA`：模块 → 列表列字段 + 表单字段
- `FORMAT_OWNER`：`atlas/xxx` 格式名 → 模块目录
- `FIELD_TITLE_DICT`：字段名 → 中文标题

运行时 `buildColumns()` 据此生成 `DataFormatColumn[]`，宽度与对齐按字段类型推断
（金额 130 右对齐、日期 120、枚举 110…）。

## 为什么不干脆把 columns 写回每个页面

会丢掉这套契约的两个好处：一是列配置可以按用户/角色做个性化（原系统真实存在的能力），
二是换主色、改密度这类全局调整只需要动一处。

## 后果

正面：

- 页面代码只声明「这一列要自定义渲染成什么」，不关心宽度与顺序；
- 表格风格统一，改一次全局生效；
- 新增页面只要跑一次脚本，列就齐了。

负面：

- 自动提取会被**详情表单**污染：如果某页列表只声明了 1 个字段列，脚本会退回去用表单字段，
  于是出现「角色列表显示权限树字段」这类问题；
- 缓解手段是 `FIELD_OVERRIDES`：给这类格式显式登记一份贴合语境的字段集，
  而不是去改生成器的启发式规则。目前已登记 9 个格式（角色、发票、资产台账、基础资料分类等）。
